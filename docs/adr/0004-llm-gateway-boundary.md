# ADR-0004：把模型治理与审计放在 LLM 网关层

- 状态：已接受（M0）
- 日期：2026-09-30
- 相关：ADR-0001、ADR-0003

## 背景

企业里"模型"这件事天然是集中式的：多供应商路由、成本与配额、模型白名单、密钥托管、合规审计（谁在什么时候
用哪个模型问了什么）。这些能力放在每个 DSH 进程里做既重复又不可控。而 Myrix 的目标是治理面，不是再造一个网关。

## 决策

**模型路由、配额、模型白名单、提示词/响应审计、密钥托管全部由企业 LLM 网关承担。** Myrix 只做两件事：

1. **下发义务**：策略里的 `rateLimit`（key + 每分钟额度）与 `modelScope`（允许的模型集合）
   随判定结果下发，由数据面转给网关执行（网关侧配置或请求头）。
2. **定义契约**（`GET /api/v1/gateway/contract`）：
   - 请求头：`x-myrix-tenant` / `x-myrix-principal` / `x-myrix-session` / `x-myrix-agent` / `x-myrix-trace`
   - 审计关联键：`traceId` / `tenantId` / `principalId` / `sessionId`
   - 网关侧落库表：`llm_gateway_calls`（provider/model/tokens/cost/latency/status/policy_revision）
3. **不保存提示词正文**：平台只存判定元数据与引用；正文审计由网关按合规要求处理（默认不入平台库）。

## 理由

- 职责单一：网关最懂模型，平台最懂授权；两者用 traceId 对齐，不互相越界。
- 成本与配额集中管控才能真正生效（跨会话、跨用户、跨租户做预算）。
- 密钥不进 DSH 运行时与用户终端，缩小泄露面。
- 审计关联而不复制，避免敏感内容在平台侧二次沉淀。

## 备选方案与为什么拒绝

| 方案 | 拒绝理由 |
| --- | --- |
| 在 DSH 里写模型路由插件 | 每个 Harness home 各自配置，无法集中管控与计费 |
| 在 Myrix 内实现一个网关 | 与"企业既有网关"重复建设；且模型供应商适配是持续投入 |
| 平台集中存储全部提示词正文 | 合规风险（数据驻留、留存期、最小化原则）；默认应避免 |

## 后果

- 正面：边界清晰，落地快；平台侧合规面小。
- 负面：依赖网关支持自定义头透传与审计落库；若网关不支持，需要在其前面加一层轻量代理（M2 任务）。
- 负面：跨系统排查需要按 `traceId` 拼接日志，平台后台要提供"按 trace 聚合"的视图（M2）。

## 验收标准（M1）

1. 一次会话中的模型调用，能在网关日志与 Myrix 治理审计里用同一个 `traceId` 关联起来。
2. 当策略下发 `modelScope` 时，网关拒绝范围外模型，并在审计中留下拒绝记录。
3. `rateLimit` 义务生效后，超限请求被网关拦截且不消耗上游额度。
