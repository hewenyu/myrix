# ADR-0003：知识库联邦与权限透传（不做 RAG 引擎）

- 状态：已接受（M0）
- 日期：2026-09-30
- 相关：ADR-0001、ADR-0004

## 背景

两件事同时成立：

1. DSH 没有 RAG/向量检索能力，也没有知识库权限模型（`packages/` 内无检索 seam，可用通道只有 MCP resources 与
   web search provider：`docs/capability-seams.md:248-249`、`packages/mcp/mcp-resources/src/tools.ts:33-52`）。
2. **企业已经有知识库，而且已经有自己的权限系统**。企业最不想要的是"平台再复制一份 ACL"——两份 ACL 必然漂移，
   而漂移的方向往往是权限放大。

还有一个硬约束：DSH 的 MCP 连接凭据是**静态配置**（`headers`/env，`packages/mcp/mcp-client/README.md:45-53`），
没有 per-user 凭据注入机制。

## 决策

1. **平台不做 RAG 引擎**（不做分块、向量化、重排的"又一个引擎"），只做四件事：
   目录聚合、跨库路由、身份透传、结果合成与审计。
2. **身份必须端到端透传**：`KnowledgeConnector` 的每个方法都接收 `SubjectRef`；平台**不使用服务账号代查**。
3. **只能收窄**：请求的 `baseIds` 与"该主体可见集合"求交；平台不提供"以平台身份扩大检索范围"的任何路径。
4. **故障隔离**：单个 Connector 失败只影响它自己的结果，返回 `errors`，其余照常（`allSettled` 语义）。
5. **两条接入路线**：
   - **路线 A（推荐，默认）**：Myrix 知识库网关 + DSH 平台工具 `myrix_kb_search` / `myrix_kb_list_bases`，
     逐调用携带主体身份。适合"知识库有 ACL API/网关"的场景。
   - **路线 B**：标准 MCP（`transport: streamable-http`，`packages/mcp/mcp-client/README.md:34-67`）。
     适合知识库侧已提供 MCP Server 的场景；但凭据静态，仅适合"服务账号可读"或"知识库侧另有令牌兑换"。

## 理由

- 不复制 ACL = 不会漂移；权限判断永远只有一处事实来源（企业知识库自己）。
- 身份透传把"平台被攻破"的最坏影响限制在"该用户本就能看到的数据"。
- 联邦层很薄（目录 + 路由 + 合并），工程投入小、可替换性强：换知识库只需实现一个 Connector。
- 检索质量（分块、重排、引用）是知识库侧的强项，交给它更合理。

## 备选方案与为什么拒绝

| 方案 | 拒绝理由 |
| --- | --- |
| 平台内置向量库 + 同步企业文档 | 需要复制正文与 ACL，合规风险高、同步延迟与漂移不可避免 |
| 用服务账号检索，平台侧再做结果过滤 | 过滤逻辑一旦有漏，就是全库泄露；且过滤依赖元数据完整性 |
| 只用 DSH MCP + 静态服务账号令牌 | 违背"用户身份查用户可见数据"，无法满足数据分级要求 |
| 在 DSH 里挂 shell hook 做检索代理 | hooks 是外部进程桥、无 run 级阻断（`packages/hooks/hook-protocol/README.md:127-129`），不适合 |

## 后果

- 正面：ACL 单一事实来源；平台侧无正文留存；接入新知识库成本低。
- 负面：**前提是企业知识库支持"以用户身份检索"**（API 网关透传、令牌兑换或 OBO）。
  若某知识库只能服务账号访问，必须由知识库侧先补一个用户态检索入口，否则该库不能接入。
- 负面：跨库结果的排序与去重是启发式的（当前按 score 归并 + 去重），后续可加 RRF/重排，
  但这属于体验优化而非安全边界。
- 待确认：企业现有知识库类型与是否已有 MCP Server（见 README 第八节问题 5）。

## 验收标准（M1）

1. 同一问题，两个不同部门的用户得到不同结果集，且审计里能看到"检索了哪些库、过滤掉哪些库"。
2. 显式请求无权知识库时，返回的 `searchedBases` 不含该库（收窄而非报错泄漏）。
3. 任一 Connector 故障不影响其他库的结果返回。
