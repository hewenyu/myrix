# ADR-0010：授权凭证（ES256 / JWS）的签发与严格校验

- 状态：已接受（v0.1 首版实现）
- 日期：2026-09-30
- 相关：ADR-0002（身份与授权）、[业务说明](../business.md)（会话绑定与租约）、[架构](../architecture.md)（身份与授权边界）。早期技术/平台草案已于 2026-10-02 本地归档，见[文档维护、归档与脱密](../documentation-policy.md)
- 实现：`packages/grant/`（`@myrix/grant`）

## 背景

控制面是唯一授权来源（ADR-0002）。cell 里的 `myrix-runtime-driver` 需要在**每条命令**上重新确认
“这条请求代表谁、要操作哪个会话、能否执行这个操作”，而 cell 不能信任路由、不能信任模型、也不能
自己保存权威绑定。平台草案（已本地归档）定的做法是：控制面在写绑定记录的事务之后
签发短期授权凭证，driver 在创建/恢复事务内校验并安装身份。

凭证的威胁模型很具体：

- 被窃取的凭证被拿去换一条消息、换一个操作、换一个会话（**凭证与请求体必须绑定**）。
- 同一枚凭证被重放（**一次性**，且必须扛得住 cell 进程重启）。
- 算法混淆（`alg=none`、HS256 用公钥当 HMAC 密钥、ES384 降级）。
- 控制面被攻破后伪造任意声明（**只能压缩攻击面，不能根治**；根治靠 KMS 与网络边界）。
- 凭证过期后仍被接受（时钟偏差、TTL 被偷偷放宽）。
- 校验失败反而烧掉合法凭证，形成可用性攻击面（**失败路径不得有副作用**）。

## 决策

### 1. 格式与算法：固定 ES256，不做协商

compact JWS（RFC 7515），header **必须恰好** `{"alg":"ES256","typ":"JWT","kid":"<轮转 id>"}`：

- `alg` 必须字符串相等 `ES256`；缺失、`none`、`HS256`、`ES384`、大小写变体一律拒绝。
  **不给“允许算法列表”配置项**——算法面越小越好，未来换算法是发新凭证格式，不是改配置。
- 签名用 `node:crypto` 的 `sign("sha256", …, { dsaEncoding: "ieee-p1363" })`，即 JWS 要求的
  64 字节原始 `R||S`，不是 OpenSSL 默认的 DER。验签侧同样显式指定，避免格式漂移。
- `kid` 是唯一的选钥依据。header 里其它字段（含 `jku`/`x5u`）**不参与任何判定**，
  不会被解析成 URL 去取钥匙（测试覆盖：带 `jku` 的伪造 token 仍然 `bad-signature`）。
- 只用 Node 标准库，不引入 JWT 库：需要的行为面很小（三段式、P-1363、SHA-256、JWK），
  自己实现比审计第三方默认值更快。

### 2. claim 表：15 个字段，逐项类型约束

| claim | 类型 | 约束 | 校验时机 |
|---|---|---|---|
| `iss` | string | 必须等于配置的签发方（默认 `myrix-control-plane`） | 绑定 |
| `aud` | string | 必须等于本 cell id | 绑定 |
| `boot` | string | 必须等于本进程 bootId | 绑定 |
| `tid` | string | 必须等于本 cell 的租户 id | 绑定 |
| `sid` | identifier | 非空、无空白、无控制字符、≤128、不含 `.` | 结构 |
| `sub` | identifier | 同上（所有者 userId） | 结构 |
| `wid` | identifier | 同上（作品 id） | 结构 |
| `preset` | string | 非空、无控制字符、≤128（preset id 含 `-`，不用 identifier 规则） | 结构 |
| `rev` | integer | 非负安全整数 | 结构 |
| `op` | enum | `create\|resume\|send\|cancel\|subscribe` | 结构 + 绑定 |
| `cmd` | identifier | 同上，且必须等于本次请求的 commandId | 结构 + 绑定 |
| `bh` | digest | 64 位小写十六进制 SHA-256，且必须等于本次请求正文摘要 | 结构 + 绑定 |
| `jti` | identifier | 同上；进程内一次性消费 | 结构 + 重放 |
| `iat` | timestamp | 非负 Unix 秒、≤2100 年、不早于进程启动时刻、不在未来（>允许偏差） | 时间 |
| `exp` | timestamp | 非负 Unix 秒；`exp > iat`；`exp - iat ≤ 60` | 时间 |

补充约定：

- **未知 claim 忽略**（前向兼容）；**未知 header 字段忽略**。两者都不参与判定，也不报错。
- 所有标识符禁止 `.`：将来若要拼复合键（`tid/sub`），不会产生歧义。
- claim 表是一等数据结构（`CLAIM_SPECS`），校验器只是遍历它，所以“每个 claim 的错误值”
  可以被测试穷举，新增 claim 必须同步补测。

### 3. TTL 60s，时钟全注入

- `exp = iat + 60`，签发与校验都强制上限 60s（`ttlSeconds`/`maxTtlSeconds` 只能 ≤60）。
  校验侧不提供“请求更短 TTL”的入口；想更短就在签发侧设。
- 时间来源是注入的 `GrantClock`（Unix 秒）。生产用 `systemClockSeconds`，测试用 `createManualClock`。
  包内**不读 `Date.now()`**（除默认时钟函数本身），也不读环境变量。
- 允许的时钟偏差默认 5s，只作用于 `exp`（`now - skew >= exp` 才算过期）和“`iat` 是否在未来”；
  **`iat ≥ startedAt` 的启动门槛不受偏差放宽**。
- 过期判定用半开区间：`exp = T` 时 `now = T - 1` 仍有效，`now = T` 起拒绝。测试锁死这条边界。

### 4. 进程启动门槛 + 一次性 jti（纵深两层）

`boot` 与 `iat` 门槛、`jti` 表三者叠加（原技术草案的裁决；草案已本地归档）：

1. `boot` 必须等于本进程 bootId。cell 重启会拿到新 bootId，旧凭证直接失效，不依赖时钟。
2. `iat` 必须 ≥ 本进程启动时刻。这一层是为了防“bootId 被复用/被猜中”的纵深；
   秒级精度与时钟偏差由 `boot` 兜底。
3. `jti` 在**进程内**一次性：`createJtiStore` 用 Map 记录，留存 120s 后惰性回收，
   并设条数上限（默认 10 万）；达到上限时**拒绝消费**而不是覆盖旧记录——宁可拒新请求，
   也不能让旧 jti 复活。重启后 Map 清空，由第 1、2 层兜底。

**消费时机是安全关键**：`jti` 只在签名、全部 claim、时间、全部绑定校验**都通过之后**才被消费。
签名错误、`bh` 不符、`cmd` 不符、过期……任何一步失败都**不消费**。否则攻击者（或一个会重试
的坏客户端）用一次畸形请求就能把合法凭证烧掉，把可用性问题变成安全问题。这条语义由
`replay.test.ts` 的三个用例直接锁死（坏签名后原 token 仍可用；绑错 cmd 后正确请求仍可用；
过期请求不写入 jti 表）。

### 5. 正文绑定：只放摘要

`bh` = 请求体的 SHA-256（小写十六进制），正文本身不进凭证、不进模型上下文、不进日志。
凭证与请求体、操作、命令三者绑定：换消息 → `bh` 不符；换操作 → `op` 不符；
换命令 → `cmd` 不符。测试断言 token 的 payload 段里不出现正文原文。

### 6. 重试规则

同一条命令重试时 **`cmd` 不变、凭证重新签发（新 `jti`）**。`jti` 管防重放，`cmd` 管业务幂等，
两者不混用。因此“同一 cmd 的第二枚凭证”必须能通过校验（测试覆盖），而“同一 `jti` 的第二份
请求”必须被拒（即使换了 `cmd` 重新签名也一样，因为 jti 的消费与绑定无关）。

### 7. fail-closed 的具体落点

- **构造即失败**：公钥集合为空、含非 P-256 曲线、JWK 带私钥材料 `d`、同一 `kid` 对应不同材料、
  `kid` 字符非法、缺少 `audience`/`tenantId`/`bootId`/`startedAt` —— 校验器根本不会被造出来。
  没有任何“运行期补救 / 退回第一把钥匙”的分支。
- **拉不到 JWKS 就是拒绝一切**：`normalizeKeyset` 对空集合直接抛 `grant/keyset-missing`；
  driver 不能以“还没配好”为理由放行。
- **错误可读且不含敏感信息**：`GrantError` 带稳定 `code`、中文 `reason`、`stage`
  （format/signature/claims/time/binding/replay/configuration）与标量 `details`；
  `toWire()` 直接给出 `{ error: "grant_rejected", code, reason, stage, details }`，
  与 BFF 的 `{ error, reason }` 错误约定同源。日志里不要写 token 本身。
- **Bearer 解析从严**：只认 `Authorization: Bearer <token>`，缺失、空、scheme 不对、
  含空白一律 `grant/malformed`；不从 query string 或请求体兜底。

## 备选方案与为什么拒绝

| 方案 | 拒绝理由 |
|---|---|
| 引入 `jose` / `jsonwebtoken` 等库 | 依赖面变大（供应链 + 默认值审计）；本包只用三段式 + P-1363 + SHA-256，几十行标准库代码就够，且行为可被测试完全覆盖 |
| 用 ES256 之外的 EdDSA（Ed25519） | 原技术草案已裁决（草案本地归档）：两者签名都是 64 字节，“更短”不成立；ES256 是各家 KMS 的公共支持项 |
| 允许配置算法列表 | 多一个配置项就多一种配错导致放行的可能；换算法应当换凭证格式，而不是放宽校验器 |
| 用 `nbf`/`aud` 数组/`scope` 字符串承载授权 | 本凭证只回答“这次请求能否投递给这个 cell 的这个会话”，不是通用 access token；授权判定在 `governance` / 绑定记录里，凭证只是它们的一次性证明 |
| 把会话正文或整个请求体放进凭证 | 凭证会被写进日志/审计；正文放请求体、凭证只放摘要 |
| jti 表用 LRU 淘汰 | 淘汰 = 让旧 jti 复活，等价于重放窗口。改为“到上限就拒绝消费”，并把上限设得远高于 60s 内的真实命令量 |
| 校验失败也消费 jti（“反正这次请求废了”） | 把可用性变成攻击面：一个持有合法凭证的坏客户端（或中间人重放畸形包）可以烧掉凭证 |
| 用 Redis/DB 存 jti 以支持多副本 cell | 一个 cell = 一个进程 = 一个租户（原平台草案 D1：一个 cell = 一个进程 = 一个租户）；跨进程重放由 `boot` + `iat` 门槛挡住，不需要分布式存储 |

## 后果

- 正面：算法与 claim 面都小且固定；每个失败路径有稳定错误码和可读原因；测试可以穷举
  “每个 claim 的错误值”；签发/校验共用同一张 claim 表，字段漂移会在类型与单测两层被拦住。
- 正面：进程启动门槛不依赖时钟精度，`boot` 由 CRD 的 `status.bootId` 提供（原技术草案的部署形态），
  路由只在 `phase=Ready` 且 `bootId` 一致时投递，两侧语义对齐。
- 负面：`jti` 记录在进程内，进程重启后丢失；这是**接受**的取舍，由 `boot` + `iat` 兜底，
  代价是 cell 重启后 60s 内的在途命令需要控制面重新签发（本来也要重新签发，因为 `boot` 变了）。
- 负面：`iss`/`aud`/`tid` fail-closed 要求 driver 启动时必须拿到 cellId/tenantId/bootId；
  拿不到就应当 ready 探针不通过，而不是“先放行后校验”。
- 负面：60s TTL 与“缩到零唤醒”耦合——cell 为零副本时不能提前签发（原平台草案的缩容步骤），
  否则唤醒完成时凭证已过期。签发必须发生在 cell Ready 之后。
- 未覆盖（明确列出，不宣称已解决）：
  - 私钥保护（KMS/Secret、签名服务隔离）不在本包范围，本包只消费注入的 KeyObject。
  - 控制面自身被攻破后可签发任意合法凭证；本包只能保证“格式与绑定正确”，不能保证“声明为真”。
  - 多副本 driver（同一个 cellId 两个进程）会让 `jti` 表分裂；当前部署模型（每 cell 一个进程）下不成立。
  - JWKS 的获取、缓存与轮转窗口由调用方负责；本包只接受已安装的公钥集合。
  - 尚未接入真实 KMS 与 driver（后续在 `plugins/myrix-runtime-driver` 集成时验证）。

## 验收标准（本包）

1. `packages/grant/src` 只用 Node 标准库，不依赖旧 `dsh-shim`（legacy，见 [legacy 参考](../integration/legacy-dsh-shim.md)）、DSH 内部类型或第三方 JWT 库。
2. 每个 claim 的非法取值都有单测负例，并断言稳定错误码。
3. 重放、过期、启动门槛、错误签名、算法混淆、kid 缺失/不匹配、正文摘要不符均有负例。
4. “校验失败不消费 jti”的语义有直接测试。
5. 本地命令：`npx vitest run packages/grant`、`npx tsc -p packages/grant/tsconfig.json`。

历史本地记录（2026-09-30，Node v24.13.0）：`packages/grant` 5 个测试文件 126 项测试全部通过；
`tsc -p packages/grant/tsconfig.json` 无错误。该数字只描述当次运行，当前以 CI 为准。
