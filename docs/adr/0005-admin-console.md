# ADR-0005：管理后台的定位与形态

- 状态：已接受（M0），认证方式待 M1 升级
- 日期：2026-09-30
- 相关：ADR-0001、ADR-0002

## 背景

"一切皆插件"让 DSH 可以按需启停组件，但**没有一个地方能回答**：谁有权限用哪些功能？为什么这个功能没开给某人？
改了授权什么时候生效？谁来审计这些变更？

同时，直接复用 DSH 的浏览器 API 做多用户后台是走不通的：现有 `/api` 是**单 operator** 模型
（Cookie 只证明"本进程的 operator"，`PeerScope` 不含身份），SDK 则面向进程外自动化且无鉴权
（`packages/sdk/server/README.md:12`）。

## 决策

1. **管理后台是控制面的一部分**，不是 DSH 的插件 UI：它是独立的、有自己认证的 HTTP/BFF 面，
   与 DSH 数据面通过判定/授权/审计 API 交互。
2. **能力边界**（M0 已实现）：
   - 概览：租户、主体、插件、高风险功能、策略修订
   - 身份与角色：主体属性、角色继承、权限点（解释"为什么有这个权限"）
   - 权限模拟：任意（主体、动作、资源、上下文）→ 判定结果 + 命中规则 + 义务
   - 功能裁剪：按主体的插件开关与原因、插件目录、授权操作、生成的 profile 补丁预览
   - 知识库：按主体可见的知识库目录与检索（验证收窄行为）
   - 审计：治理决策与变更事件
   - 模型与审计边界：网关契约（让"模型治理在网关"这件事可见、可对接）
3. **认证（M0 → M1）**：M0 用静态 Bearer 令牌（启动时若为默认值会告警）；M1 接 OIDC，
   后台账号单独建 `console_operators`（viewer/operator/admin）映射，不回灌到 DSH。
4. **写操作必须留痕**：任何授权/策略变更写 `audit_events`（`admin-change`），包含操作者与变更内容。

## 理由

- 治理后台天然是**跨 DSH 实例**的（多租户、多 home），把它做进某个 DSH 进程会限制视野。
- 独立面可以用企业标准方式做认证、审计、备份、灰度，不受 DSH 版本演进影响。
- 与 ADR-0002 的 BFF 方案天然同构：将来若需要"在 DSH 内部看到治理面板"，可以再加一个 client 插件
  调用同一个控制面 API，而不是把逻辑搬进 DSH。

## 备选方案与为什么拒绝

| 方案 | 拒绝理由 |
| --- | --- |
| 复用 DSH `/api` Remote + client 插件 | 单 operator 语义、无身份维度，且与上游 UI 强耦合 |
| 用 DSH SDK 做后台后端 | stdio JSON-RPC、无 HTTP、无鉴权、方法集极小（`initialize/prompt/shutdown`） |
| 在 DSH 内起第二个 WebServer（`cordis:group` + `isolate.webServer`） | 技术上可行（仓库有 GitHub webhook 先例），但把控制面绑进数据面进程，运维与升级耦合 |
| 命令行管理（改配置/跑脚本） | 不可审计、易出错、无法解释"为什么" |

## 后果

- 正面：后台与数据面解耦；后台可独立审计与扩容；同一套 API 也能被 CI/自动化调用。
- 负面：需要单独部署与运维一个服务；M0 前端是无构建依赖的原生实现（故意为之：先验证信息架构，
  再决定是否引入 React/Vite）。
- 负面：认证在 M1 前是静态令牌，只适合内网演示。

## 验收标准（M1）

1. OIDC 登录后，`viewer` 只能看，`operator` 能改授权，`admin` 能改策略，且全部变更进审计。
2. 后台展示的"某主体功能列表与原因"与运行时 `ctx.tools.restrict` 实际掩码一致（有对照测试）。
3. 撤销授权后，profile 预览与运行中掩码都在承诺时间内收敛。
